[1] Question: was phase 1 useless because no ticks were sampled for intervention
    (few gated ticks per 3 s window x p_branch = 0.1)?

Answer: no. Interventions were sampled. The result is still useless, but for a different reason.

  Sampling (runs/pick_v2, phase 1):
    - 3096 rollouts, 3050 branch points; every branch point runs both a no-op branch and an
      intervention branch, and both samples go to replay (810 random eps + 2240 greedy corrections).
    - The rate estimate was right: ~10 gated ticks/rollout x 0.1 = ~1 branch/rollout. The code makes up
      for the low rate by running >3000 rollouts.
    - Misleading log fields:
        * rollout.interventions = 0 counts trigger firings on the main rollout; the trigger is off
          in phase 1 by design.
        * gated_ticks ~= 1.0/rollout in phase 1 is a counting artifact (rollout.py ~l.233: a tick
          counts as gated only when observe() runs, i.e. only on branch ticks). The true figure,
          9.7/rollout, shows in phase 2.
    - Phase 2 also finished: 1000 branch points, 3 trigger firings.

  Real problem: corrections almost always fail.
    - Pick success within 3 s: no-op 1122/3050 (37%) vs intervention 87/3050 (2.9%).
    - Of the 1122 states where pi0 alone succeeds, the correction ruins 1042; it rescues only 7 states
      where pi0 fails.
    - So the Q-map learned "never correct" (Q(a) ~0.02 vs Q0 ~0.23); A(s) is useless as a trigger.

  Cause: how execute_primitive (libero_env.py:236) spends its 30-step budget (prim_cap = 1.5 s):
    - The "rise" leg (clearance) fires in 78% of corrections, since the gripper is near the target and
      below h_clear + 2 cm. It uses ~22 of the 30 steps.
    - So the move leg is skipped in 53% of corrections and reaches its goal only 19% of the time.
    - 83% of corrections use the full 30 steps. The 3 s label clock (H_max) starts before the
      correction, so pi0 has only ~1.5 s left to pick, against 3 s in the no-op branch.
    - In practice the correction mostly lifts the gripper away from the object just before pi0 would
      grasp it. The chosen cell/yaw barely affects the outcome, so there is nothing spatial to learn.

  Possible fixes (none applied yet):
    1. Rise: skip or limit it for small sideways moves, or rise only as far as the move needs.
    2. Label timing: start the H_max window after the correction ends, or give the intervention branch
       extra time equal to the correction's duration.
    3. Budget: raise --prim-cap, or split it per leg so the move leg can't be starved.
    4. Logging: count gated ticks from gate_open in phase 1.
    -> Phase 1 needs rerunning after 1-3; the current checkpoint is just "never correct".

[3] Question: Q0 is trained only on no-op labels. Does Q0 then automatically mean "let pi0 continue",
    even though the action A0 nominally means "level first"?

Answer: yes, by construction. The A0 entry of the Q-map is only a slot for the no-op value.
    - Phase 0: only (obs, A0, y_noop) is pushed; the level-only probe results are measured but not
      pushed (replay_phase0 noop_frac = 1.0).
    - Phase 1/2: each branch point pushes (obs, A0, y_noop) plus (obs, a, y_a) for a correction a.
    - correction_actions() (qnet.py:66) removes A0, so neither the eps-greedy branches nor the trigger
      ever execute "level only". Q0 is never trained on a levelling outcome.
    - So A(s) = max_corr - Q0 compares each correction with "pi0 continues", which is the right
      comparison for the trigger.

  Consequence 1: the "no-op ~= level only" assumption is false, so A0 breaks the continuity of the map.
    - phase0_report.json: levelling alone lowers the label in every tilt bin
      (0-10: -0.06 [z -2.1], 10-20: -0.14 [z -5.3], 20-30: -0.10 [z -3.8], 30+: -0.26 [z -7.1]).
      The report recommended training Q0 only below some tilt, or a separate V network (sec. 15).
      Phase 1 went ahead anyway (no tilt restriction).
    - Phase 1 confirms it: same cell, yaw only (level + rotate in place, cheb 0, yaw != 0):
      y_a 0.047 vs y_noop 0.428.
    - So the map must put ~0.2-0.4 at one entry (k=4, cell 5,5) and ~0 at its neighbours, including the
      same cell at +-5 deg yaw.

  Consequence 2: the architecture gives the network no clear signal that the centre cell is special.
    - Shared FCN trunk + 1x1 heads + global-mean context (shared/fcn.py); no coordinate channels.
      Q0 shares the k=4 output channel with every yaw-0 cell, and its spatial position with the 8 other
      yaw bins.
    - The map is gripper-centred, but robot pixels are masked out of the heightmap, so "this is the
      centre" can only come from zero-padding edge effects / receptive-field position.
    - On average it fits (train log: Q0 pred/label 0.23/0.23, Qa 0.02/0.02), but the gap between Q0 and
      the neighbouring entries is learned weakly, and corrections nearly always fail, which hides how
      weakly.

  Suggested direction (not applied): a separate V/Q0 head (e.g. an MLP on pooled trunk features +
    proprio) for the no-op value, with the Q-map covering corrections only. Alternatively, add a
    coordinate / centre-indicator input channel. Either way, keep the rule that Q0 is trained only on
    y_noop.

[4] User proposal: use a separate value function V(s) for the no-op value within the time window.

Agreed. pixel_Q_RL_V2.md sec. 15 already describes it, and its first switch criterion is met: phase 0
shows levelling changes the outcome at every tilt. Discussion points:

  Design (sec. 15 + suggestions):
    - V(s): small CNN on the same heightmap + proprio -> scalar; an ensemble (K heads) so it has
      sigma_V too. Trained on y_noop only. Trigger: A(s) = max_a [mu_a - kappa*sigma_a] - V(s).
    - Train V first, then freeze it while the Q-map trains (sec. 15), or train both with separate
      optimizers and batches.
    - The centre cell at 0 deg becomes an ordinary, executable correction ("level only"); remove the
      A0 exclusion. Phase 0 is then no longer a precondition.

  Data for V (main win):
    - The main rollout in phases 0/1 is itself a no-op trajectory (pi0 + HL, no trigger), so every gated
      tick gets a free y_noop label from the main rollout's own future: gamma^(dt/20) if pick happens
      within H_max, else 0. That is ~10 labels/rollout instead of ~1, with no extra simulation (labels
      within a rollout are correlated).
    - Exclude ticks whose label window contains an HL correction or trigger intervention (no longer
      pi0 alone).
    - Needs a code change: store obs at every gated tick (currently observe() runs only on branch
      ticks), then label it when the rollout ends.
    - Existing data: ~4400 branch no-op labels in replay.pkl (phase 0 + 1 + 2) can be used to
      pretrain/validate V right away, with no new simulation.

  Must fix together with V: V and Q must predict the same quantity.
    - Both labels should be measured from the branch tick with the same gamma^(t/20) and the same window.
    - Do not restart the clock after the correction for Q only; that gives corrections free time and
      biases A upward. The discount already charges the correction for its duration (fair).
    - Instead make the window long enough for correction + pi0, e.g. H_max >= 3 s + prim_cap (1.5 s);
      phase 0 found no-op success p90 = 5.8 s, so 5-6 s is reasonable for both.

  Risk (sec. 15 "Cost"): errors no longer cancel. With a shared Q0, a misjudged scene shifts Q0 and Q(a)
    together; with separate networks it does not. Check at branch points (paired labels from the same
    state) whether the V-vs-Q error offset is constant (absorbed by tau) or varies by state. Fallback:
    a dueling architecture, Q = V + Adv(a).

[8] Q: what are the "proprio only" rows, R2 and AUC?
    - proprio only: baseline V that sees only the 4 proprio numbers (finger gap, sin/cos tilt, height above
      target top), no heightmap. The gap to the CNN = what the heightmap adds.
    - R2 = 1 - MSE(V) / MSE(constant train mean): 1 = perfect, 0 = no better than always predicting the
      average, < 0 = worse. Measures whether the predicted value level is right.
    - AUC: chance that a random success state gets a higher V than a random failure state. 0.5 = random,
      1 = perfect ranking. Ignores level/calibration; measures ranking only.

[16] User doubt: once V is trained, why a Q-map? V alone could guide the gripper. (1) The Q-map gives the best
     cell from the current observation only (efficient). (2) "If V < threshold, sample N poses, argmax V(pose)"
     needs the observation at each pose: either physically move there (slow, sequential) or a model that maps
     pose -> expected observation.

  Discussion:
    - Agreed on (1): Q(s, a) is an amortised "value after moving by a", predicted without the post-move
      observation. But it needs a label per (state, action) out of 441 actions (sparse; part of why V2 phase 1
      learned little), while V gets a dense label for every state it visits (natural or perturbed).
    - On (2), the pose -> observation model already exists, almost for free: V2's heightmap is built from a world
      point cloud (agentview + wrist depth, robot points removed), rasterised around the grasp point p with yaw
      psi; the height channel is relative to p_z; proprio = finger gap, tilt, p_z - target top. For a candidate
      pose (p', psi', tilt'), re-rasterise the SAME cloud around p' with psi' and recompute proprio -> a synthetic
      observation. No sim, no robot motion; N candidates = N rasterisations + one batched V forward (ms-scale on
      GPU, ~0.1-0.3 s for ~64 candidates in numpy, and only needed when V < threshold).
    - Differences from the real arrival observation: the wrist camera would see from a new viewpoint (different
      occlusions / holes, filled from agentview or left unobserved); otherwise geometry is the same.
    - V(s') then plays Q's role if V is trained on "move a little, then pi0" data (the perturbation episodes)
      with the clock starting at arrival; the move cost can be added as gamma^(t_move). Trigger becomes
      max_c V(s'_c) - V(s) > tau.

      ever matters.
